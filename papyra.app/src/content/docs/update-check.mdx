Papyra has no tracking, analytics or crash reports. It makes **one** request of its own,
once a day, and this page is all of it.

## What it does

Once a day your server asks `versions.papyra.app/latest.json` for the newest release.
If a newer one exists, admins see a small warning icon beside the version in the sidebar;
it opens a popup saying how to update. Other accounts never see it.

The code is short and meant to be read:
[`papyra.api/src/Papyra.Api/Storage/UpdateCheck.cs`](https://github.com/lyfie-org/papyra/blob/main/papyra.api/src/Papyra.Api/Storage/UpdateCheck.cs)
is the whole client, and
[`papyra.versions`](https://github.com/lyfie-org/papyra/tree/main/papyra.versions)
is the whole server.

## What it sends

Four facts, in the address of the request:

```
GET https://versions.papyra.app/latest.json?id=2d1f0c2e-…&v=1.0.0&arch=arm64&os=linux
```

- **`id`** — a random ID your server made the first time it asked, kept in `.papyra/instance-id`
  in your data folder. It is not derived from anything: not your hostname, your address, your
  accounts or your notes. All it can say is "the same install again". (Delete `.papyra/instance-id` to get a new one.)
- **`v`** — the version number you run, such as `1.0.0`. A development image reports its development
  version, such as `1.1.0-dev.abc1234`.
- **`arch`** — the processor family: `x64`, `arm64` or `arm`.
- **`os`** — the operating system family: `linux`, `windows` or `macos`.

It does **not** send notes, titles, usernames, emails, your server's name or address, how many
accounts you have, or anything about how you use Papyra.

## When it asks

Once a day, at a time of day each install has to itself — worked out from its random ID, so it is the
same every day and nothing has to be stored. That spreads check-ins over the day instead of bunching them
up. A restart doesn't ask again. Nothing is ever sent between 02:30 and 03:30 UTC (08:00–09:00 IST): that
quiet hour is when the site is rebuilt from the day's numbers.

## What the project does with it

- The IP address of the request is **never stored**. Cloudflare turns the connection into a
  two-letter country code at its edge, and only that code reaches the code that counts. There are
  no access logs and no request logging on the Worker.
- One row per install is kept: the random ID, the version, the processor and OS family, the country, and the
  first and last day it checked in. That is the whole table ([`schema.sql`](https://github.com/lyfie-org/papyra/blob/main/papyra.versions/schema.sql)).
- From it come three numbers: installs ever seen, installs active in the last 30 days, and the
  countries, versions, processors and operating systems they run. They are public at
  [`versions.papyra.app/stats.json`](https://versions.papyra.app/stats.json) and shown on the
  [home page](/#privacy).

## When there is a gap

"Active in the last 30 days" is counted back from the newest check-in the project has, not from the
clock. If check-ins stop arriving for a few days — a glitch, an outage — the numbers stay where they
were instead of draining away, and they update again as soon as check-ins resume. The public number of
installs only ever goes up, and the last good numbers are kept in case the live ones can't be worked out.

## Why I count

I count installs because it keeps me motivated to build more cool things, and it feels good to
see that Papyra is actually being used. That, and telling you when there is an update, is all
this is for.

A server with no release version at all (`dotnet run`, the test suite) never makes the request, so
developing Papyra doesn't count as installs.
